# Rules

Generated by `esoi rules --markdown`; each problem line printed by `esoi check` starts with the id of the rule it breaks. Records are checked by rules R1 to R5 inside S26 (R5 is the parent and retired-column check). S28 and S29 apply only to the intent layout, where the configured folder holds a project's top intent (why the project exists, in its own words, never ESOI by default) and each subfolder with its own `intent.csv` is a sub-intent; the evolvable structure a project applies is a solution inside its top intent, whose implementation may use esoi solutions (`uses_solution_ids`, written `@project_id/solution_id` for another project).

- **S1** Every file belongs to exactly one component and every component path glob matches a file.
- **S2** Every component row has a role and a layer from the configured set.
- **S3** No Python file at the repository root (unless root_python_files is set, the file is listed in root_python_allow, or a waiver names it).
- **S4** No Python module over the size ceiling (max_lines); split by role or waive with a reason.
- **S5** Every module of the package opens with a docstring that states its role.
- **S6** Dependencies point inward: a module imports its own layer or a lower one (TYPE_CHECKING imports ignored).
- **S7** Every Protocol class is in the port cell of some solution; implementation paths and metric scripts exist; selected is a listed implementation or a selection-table name; no metric means a gap and an action.
- **S8** COMPONENTS.md matches components.csv, and each intent folder's README.md matches its records (esoi check --write-docs regenerates them).
- **S10** An eval solution's selected implementation has a recorded row and no rival beats it, or a waiver names the pending decision; an invariant solution is never ranked.
- **S11** Every solution is eval or invariant (an invariant states invariant_reason), is linked from some component, and every linked id exists.
- **S12** Every evaluation implementation drives live package code or declares itself an alternative (ALTERNATIVE = True, or a docstring opening ALTERNATIVE, BASELINE, ABLATION, FLOOR or VALIDITY); a selected or measured implementation must be live, or waived.
- **S13** A layer (or path prefix) listed in [rules.S13] reads no environment variables; the value is passed in.
- **S14** Every solution with a port has a selection-table entry and no entry lacks a row; a default, when the entry holds one, is one of its implementations and each implementation's module is listed in the row's implementations cell or in the `path` of one of its implementations.csv records (several implementations may share a module).
- **S16** The latest results row of every implementation carries a cases_sha, or a waiver says why not.
- **S17** The tracker tabs match what the registry and the results log now produce (only tracking_* columns are hand-edited). Checked when the tracker folder exists.
- **S18** Solution and component ids are unique and no id repeats inside one cell.
- **S19** Every component names at least one solution.
- **S20** Every solution has a problem, an ideal, a metric, implementations, a selected implementation and a recorded run on the current cases with a git_sha; tests alone are not a metric. With --strict the run must also be on committed code that has not changed since, and so must every rival it was compared with (waive one rival as `<solution>:<implementation>`).
- **S21** Every evaluation folder is named by some solution's metric command, or is listed as shared.
- **S22** No score, percentage, dollar amount or case count in a gap, an action, a waiver reason or a record field, except a solution's milestones, which state target values of metrics; numbers measured live in the results log.
- **S23** For a solution whose selection-table entry still holds a `default`, selected equals it (an entry with no `default` takes the records' `selected`, so there is nothing to compare).
- **S24** Every arm a metric command names has a results row, and a gap or action that says an implementation is not recorded names none that already has a row.
- **S25** An invariant solution's evaluation folder has a broken/ baseline module besides __init__.py.
- **S26** The intent records fill every field of the evolvable-structure template and link as it says (a problem is not a task, every problem has a solution and an ideal, links agree both ways), and parent links resolve (in the legacy layout, to the overall network; in the intent layout, anywhere in the tree).
- **S27** The committed template copy equals the source it was parsed from (skipped when the source is not reachable).
- **S28** Each intent folder has one intent.csv row with a unique intent_id and every field of the intent template; the top intent leaves implements and opportunity empty; a sub-intent is in a folder named by its intent_id, names, in implements, an implementation of its parent intent, that implementation names it back in sub_intent, and the sub-intent states the opportunity that justifies it.
- **S29** A record id is used once across the whole tree (also across record types and intents), and every uses_solution_ids entry names a solution somewhere in the tree other than the implementation's own, or is written @project_id/solution_id for a solution of another project (listed in the local ESOI index, not read here).
- **S30** Every solution and implementation declared in the measured code (@solution, @implementation, register) has its solutions.csv row and implementations.csv record, and the record's path is the declaring file; `esoi records sync` writes the missing rows.
- **S31** A metric is meaningfully real: no implementation in a metric's evaluation folder declares SIMULATED = True, and no metric record describes its judge or model as scripted, simulated, mocked or a stand-in (or a waiver names why that metric cannot be real).

The legacy two-level layout (an `overall` network beside the detailed records) still loads and passes these rules. `esoi check` prints one note for it, pointing at [the migration guide](../../../docs/guides/migrate-to-intents.md), and `esoi intent migrate` does the mechanical part. A solution whose `metric_kind` is `specification` is defined and has alternatives but no run measures it yet (its chosen implementation builds on other solutions, or is a document); rules that need a metric command, a component or a recorded run apply to the other solutions.
