- **S57 counts copied logic, not shared shape (Joshua: every advisory must be worth doing).** A copy is now a stretch of at least 40 matching tokens (`Budgets.clone_run`) that holds at least 3 deciding, looping or computing tokens (`Budgets.clone_logic`), and constant registration decorators and Protocols are declarations like constant tables. On this repository the copied share fell from 9.0 to 0.5 percent of the code and the files with a finding from 246 to 26; a seven-line function copied into six files and a 30-line block copied once are still found (tests in `tests/test_structure_quality.py`). A file is listed (a to do) only when 15 percent of its tokens are copied (`Budgets.clone_list_share`), or a copied stretch appears in 3 or more files (`clone_list_files`), or 150 of its tokens are copied (`clone_list_tokens`); smaller copies stay in the score and show as "smaller copies" in `esoi structure-quality`. That leaves no S57 to do on this repository (it was 51 findings). Also written once: `assemble.package_assembler`, `results_log.latest_by_impl`, `expect.pass_counts`. - **`esoi check` no longer counts a stale recorded result as a to do unless the situation makes it matter.** S20 findings used to appear under "to do: N finding(s) of the advisory rules" after almost every code change, though the metric run policy says a stale row only informs. Now a stale result (other cases, changed or uncommitted code, changed circumstances, a rival recorded earlier) is one line, `info: N recorded result(s) describe older code; `esoi run --stale --plan` lists them`, outside the to-do count, and `esoi check --findings` and `--strict` list each in full under it. It is a to do only when its metric's `expiration` (or the project's `[expiration] default`; never by default, and never in this repository) has passed, or when `esoi check --for-decision` says a decision or release depends on the results (the same idea as `esoi run --stale --for-decision`). A malformed row (no `git_sha`, no `cases_sha`, unreadable `circumstances.csv`) still fails. New: `check.check_report` returns `(problems, advisory, information)`; `check_all` is unchanged. Docs updated (choose-when-a-result-is-stale, when-metrics-are-run, apply-with-tools, attest, the metric run policy, rules S20).

- **Structure Quality scope: an arm off its interface is scored by how far off, layered Protocols are not a split signal, and a compare leaves no temporary checkout (Joshua: the merge that stripped Protocols from 22 interfaces must show as a fall).** The `arms_on_interface` part is the mean of each arm's share of its Protocol's members implemented, cubed (the reuse curve), a Protocol counts the members of the Protocols it extends (an empty extending Protocol let every arm pass), and an arm off its solution's interface that implements a plain Protocol beside it is told its interface was demoted. The Protocols-per-folder check counts groups: Protocols the same arms implement, or layers where an arm takes exactly one Protocol of the folder as its constructor need, are one job; Protocols that different arms implement stay reported. The weights are unchanged. - **Structure Quality: a shared kernel is not coupling, size is graded, and five gaming moves are closed (Joshua: "have /joshua on opus improve the metric(s) for code quality/structure").** An import of the project's shared kernel (imported by three or more units, instability at most 0.2, depending on no solution, every name taken by two or more units) counts as clean; on three repositories with history such imports changed with their target 1.4 to 19 percent of the time against 6.4 to 47 for other reach-ins. Size counts lines over budget instead of a count of long functions and adds McCabe complexity (budget 10). A stub member does not implement an interface, an arm that passes every call on unchanged counts against scope, the Protocol members callers use join the surface, and names passed on by `import *` are followed. Cases SQ-029 to SQ-041; the guessed history pairs replaced by real commits; reference line re-measured (0.75); a how-to section on reading the report and a plain list of what the number cannot tell a reviewer.

- **Structure Quality coupling: front doors and declared entries are not offenses (Joshua: coupling "scores 0.09 to 0.20 on every repo, and much of it is false").** A project's front door (`api.py`, `__main__.py`, the top package `__init__.py`) is no longer counted as a cross-solution caller or a source in the cycle graph, and an import of a unit's `interface.py`, `__init__.py`, an `implementations.csv` filepath or a module that declares `@solution` or `@implementation` stays clean. A name taken from a front door is followed through its re-exports and counts as an entry only when it resolves to one of those, so moving every import behind a re-export hides no reach-in. Offenders read "imports X inside another unit; its entry point is Y"; the rule is in the coupling section of `docs/explanation/code-quality-is-structure-quality.md`. Cases SQ-026 to SQ-028 (front door clean, reach-in, reach-in behind the front door). Measured on four repositories the change is under 0.02 of coupling each: the offenders that remain are real reach-ins, and the eight git-history rows keep their direction.

- **Structure Quality measures and optimizes a restructuring (Joshua: "the esoi structure check for quality structure you recently added should be how it measures and optimizes this").** `esoi structure-quality --compare <before> <after>` (and `compare_structure_quality` in the public API) prints the balanced number and each dimension before and after, the offenders fixed and introduced and the per-solution scope and per-unit coupling deltas; each side is a folder or a git reference, checked out into a temporary worktree and removed. An arm must implement every member of its Protocol with matching parameters under a solution id that exists, resolving Protocols and base classes of adopted libraries and installed packages; reuse is a graded curve with boilerplate families reported apart from accidental clones; an interface module's Protocol reached by `run("id")` or a type annotation counts as used; a dimension that cannot be measured is named with its weight shared out; the 0.80 pass mark is replaced by a reference line derived from measured kept structures; a file is read once per content through the shared cache and the walk of record files happens once. The order of building, the how-to, the explanation, CLAUDE.md and a tagged standard (`restructure-by-structure-quality`) say that every restructuring is measured before and after.

- **Structure Quality: one balanced number for how well a project divides its work (Joshua: "what guidance or approach or metric can we define so esoi ensures high quality coding in terms of proper solution scoping and modularity across different dimensions").** A solution of the Structure container, with seven offline dimensions (scope, size and cohesion, coupling, reuse and duplication, flow fidelity, public surface, behavior preserved) at fixed weights, a stage that mines co-change from git history, and a paid expert review that is specified and costed but not run. `esoi structure-quality [--stage 1|2] [path]` prints the number and the worst offenders (advisory, always exits 0); the advisory rules S54 to S59 report the same findings in `esoi check --findings`; the cases include a project cut into tiny files, which must score below the balanced real structure that a size-only scorer prefers. The word-overlap measure of S48, S49 and S53 now lives in `esoi.structure.structure_quality.overlap`. Docs: [code quality is structure quality](docs/explanation/code-quality-is-structure-quality.md) and [measure structure quality](docs/how-to/measure-structure-quality.md); the order of building asks for the scoping review when interfaces are written.

- **Generated READMEs: a labelled vision at the top, one level below, two kinds of page, a breadcrumb, and the generated note last (Joshua: "its hard to find the vision statements in readmes").** Every page shows `**Vision statement:** <statement>` directly under the title. An intent page adds "One level below": each sub-intent with its vision statement and each solution with its purpose, every child linked and named by kind (`sub-intent`, `solution with implementations`, `solution with no page of its own`). A solution folder is not an intent: it shows its own `**Purpose:**`, role (out of scope, delegates to) and `Part of <immediate parent>`, never an ancestor's vision or paragraph, and a leaf solution (implementations only) has no children section, so the bottom of the hierarchy is visible by structure. Every page opens with a breadcrumb (`Top > ... > this`) and ends with the one-line generated note instead of starting with it. Arm pages written by an older version have the note at the top and are no longer recognised as generated: delete them and run `esoi readmes`.

- **An adopted solution takes the adopter's own arms, metrics, ports and components, and its id resolves everywhere a solution id does.** Adopted rows used to be kept out of the solutions list, so every rule and the run-time selection saw the adopter's arms, metrics, ports, components and `uses_solution_ids` that named one as dangling (S7, S11, S21, S26, S29). The registry now loads an adopted row as a solution (`Registry.every_solution()`, `solutions`, selection, lock, stale planning, tracker and pages see it), keeps `Registry.adopted` as the list of them, and offers `Registry.authored()` for what reads a solution's own words; the rules that need those words (S20 problems and ideals, S26 template fields, problems, ideals and metric, S46, S48, S50) skip adopted rows. Also fixed: the coherence code evidence (S38) compared a whole multi-name `interface_name` cell instead of each name, so code evidence was lost when an interface moved.

- **A repository can adopt solutions from another library's records (rule S53, advisory).** A row of `solutions.csv` with an `adopts` cell (`@library/solution_id`, the library named under `[adopts.<library>] repo` in `esoi.toml`) is a reference only: it carries no vision, problems, ideals or role of its own, may add its own arms that compete under the library's metric, and is shown on the generated page as a link to the library's page with the library's own description. A `specializes` cell marks a solution that needs the application's data; every other solution is the application's own. S53 informs of an unresolved reference, an adopted row that restates the library, an own solution that says the same job as a library solution, and an arm that does not declare the library's solution id. New solution Library Adoption under Structure; explanation `docs/explanation/adopting-solutions-from-a-library.md`, how-to `docs/how-to/adopt-a-solution-from-a-library.md`.

- **Know What a Result Measures declares its interface where it lives.** `esoi.staleness.stale_results(project)` is the solution's one line (rule S37), with the three rules `repo_wide`, `component_paths` and `import_closure` as its implementations; `esoi.run("know-what-a-result-measures", ".")` returns the latest results that no longer describe the code they measure, each with the changed file. esoi's own runner now loads `esoi.staleness`.

- **Problems say what is true; ideals say the state that is wanted. Rules S51 and S52, an explanation and a how-to.** Joshua, on a problem that read "nobody tests the whole": "this isn't correct ... what developer would say that", and problems need "nuanced yet clear and simple language"; on ideals: "absolutes are more expected in ideals than in problems", and "ideals should avoid being solutions ... ideals are the state we want." `docs/explanation/a-problem-says-what-is-true.md` says why, `docs/how-to/write-problems-and-ideals-that-hold-up.md` is the checklist with before and after examples. New advisory rules (inform, never fail): S51 points at a sweeping absolute in a problem's text and asks whether it is literally true and what the real gap is (what is missing, for whom, how often, at what cost); ideals are not read. S52 points at ideal text that reads like a solution (opens with an instruction to build or use something, or names the means) and asks for the state instead. Waive a true one as `record_id:field`. The scaffold's own problem no longer says "never" or "nobody".

- **Role scoping of solutions: `delegates_to`, `change_driver`, rules S48 and S49, and a how-to.** Joshua: the nuances of scoping a solution's role were hard to consider proactively, so esoi should encourage specialization and delegation of responsibility. `solutions.csv` gains two standard columns (R7 accepts them; `esoi init` writes them): `delegates_to` (the ids of the siblings that own what the solution excludes, or `none`) and `change_driver` (for a container, what kind of change moves its metric: outside systems, the system's own data model or code, ML task accuracy, alignment with humans or policies). New advisory rules: S48 (a solution with siblings that states no exclusions; exclusions with no named owner; a delegation to no solution; two siblings whose purpose and description overlap strongly; a container with no change driver) and S49 (a review prompt, not a verdict, for a solution with three or more implementations whose descriptions share little). The `out_of_scope` template question is unchanged (it asks not to name other solutions), which is why the owner goes in `delegates_to`. `docs/how-to/scope-the-role-of-a-solution.md` is the checklist. Migration: add the two columns to `solutions.csv` and scope each role; until a repository has a `delegates_to` column it gets one S48 line per intent.

- **A solution is a container for alternatives that do the same job (docs).** Joshua's lesson, `docs/explanation/a-solution-holds-alternatives-of-one-job.md`: when an implementation list mixes purposes or very different specificity (a solution named Acting whose arms are a one-call file edit, an MCP write and Claude Code runners), the solution is mis-defined; split by purpose into a general solution with general arms and specific solutions nested beneath or composed by it (optionally routed cheapest-first), and name the general alternatives that are missing. It belongs to the step that defines solutions and to the review step. No rule: grouping arms by what their descriptions say is a judgement, and a word-overlap heuristic would only flag solutions whose arms are described differently.

The migration is mechanical and writes no wording: sentences that state exclusions ("avoids", "is not", "does not") move whole to `out_of_scope`, the rest stays as `purpose`; for a metric, only a sentence saying what it cannot see moves to `disadvantages`; `description`, `approach`, `tags` and a new `disadvantages` stay empty for the owner to write (R2 reports them).
- **A tool or an AI does not add specification fields on its own.** Rule S26 (R7) now fails when a records file has a column
  that is not a field of the template, not technical (an id or link ending `_id` or `_ids`, `filepath`, `command`,
  `interface_name`, `implementations`, `selected`, `sub_intent`, `implements`, `tracking_*`; the one list is
  `records.TECHNICAL_COLUMNS`) and not approved by the specification's owner in `esoi.toml` under `[records.approved_fields]`. The message
  says to propose the field to the person who owns the specification. The scaffold, `esoi records sync` and `esoi add` no
  longer write `selected_by`; `esoi select --promote` stores its evidence there only where the project approved the column,
  and prints it otherwise.
- **Every metric outputs a number, so there is no metric kind.** The solution columns `metric_kind` and `invariant_reason` are
  removed: a rule that holds or does not is measured as the pass rate on its cases, ranked like any other, and a solution
  with a single implementation keeps a deliberately naive baseline in `broken/` that its cases must fail (S25). A solution none
  of whose metrics has a command that records a run (`esoi run <component> --impl <name>`) is a specification, derived and never declared. When a solution has
  several metrics, the new link column `authoritative_metric_id` names the one that decides which implementation is best (R6).
  `gap` and `action` are removed too: a next step is a milestone (a value of a metric), and what a metric cannot see goes in
  the metric's `scoped_purpose`. A repository with the old columns gets an R1 finding that says where each one's content goes.
- **An empty `milestones` or `opportunities` is allowed.** `records.MAY_BE_EMPTY` names the two template fields a record may leave empty: a solution with no milestone has none its owner has chosen, and an intent need not state opportunities. Every other template field is still required (R2), and a sub-intent still states its opportunities (S28).
- **Three record columns renamed.** `solutions.csv` `port` is `interface_name`, `implementations.csv` `path` is `filepath` (components and waivers keep `path`), and `intent.csv` `opportunity` is `opportunities`, now a field of the Intent template for every intent (the top intent states its own). A repository with the old headers gets an R1 or S28 finding naming the new column, not a crash; there is no migration. The `port` keyword of a code declaration is unchanged.
- **A solution has Milestones, not Goals.** The solution column `goals` is now `milestones`: the solution's priorities in order, each a value of one or more metrics, with an optional end condition (when it stops being a priority and is archived) and an optional target time (a planned completion, which is not an end condition). The template parser attaches lines indented under a field to that field's question as guidance instead of reading them as new fields. Rule S22 lets `milestones` state target values. The implementation description asks how it achieves the purpose of its solution's definition. Standing conditions belong in `measures_of_success`; a constraint shared by many intents is specified once in its own intent, not as a milestone of each solution it limits. Existing records: rename the column and sort each cell.
- **Rule S31: a metric must be meaningfully real.** `esoi check` reports an implementation in a metric's evaluation folder that
  declares `SIMULATED = True`, and a metric record that calls its judge or model scripted, simulated, mocked, stubbed, fake, canned
  or a stand-in; a waiver names why a metric cannot be real. Documented in `docs/explanation/metrics-must-be-real.md`. The
  `spec_index` cases were strengthened with longer, noisier requests, two-record requests and requests that concern nothing, so
  the two implementations no longer pass nearly the same cases.
- **Specification index.** `esoi spec index|find|show` and `esoi.spec_index`: a deterministic, non-AI JSON map of the records (stable
  ids, tier-0 and tier-1 descriptions, two-way links, weighted terms, document frequencies, digests) for finding the few
  specifications a new use case needs. Solution `spec-index`, metric `metric-spec-index-recall`. No vectors or models here: a
  system on top adds them. See `docs/explanation/finding-specifications.md`.

Graceful declarations (declare once where the code is; derive or check the rest). See `docs/explanation/graceful-selection.md`
and the migration steps in `docs/guides/migrate-to-intents.md`:

- **Scopes, older variables and installed packages.** Two packages in one process may declare the same solution id: a
  declaration belongs to its package, and `resolve(id, scope="pkg")` reaches that package's alone (scoped variable
  `ESOI_SELECT_<SCOPE>_<ID>` first). A scope also tells the lookup where to start before anything is imported, and the
  folders around a package installed into `site-packages` are not searched for records (it reads its snapshot). `selection_env`
  in `esoi.toml` keeps an older environment variable working, named in the error. An unknown solution lists the solutions that
  have implementations; `explain` returns where each name came from. `register(..., replace=True)` lets a consumer put its own
  implementation under a name a package declares, whichever is imported first.
- **Gentle default folder.** When `structure_dir` is not set and `esoi/` does not exist, a previous default (`docs/structure`,
  `structure`) that holds records is used, with one note suggesting `git mv docs/structure esoi`. Two folders holding records
  are never guessed between: the error names both. The same resolution serves `esoi projects` and the consumer check.
- **Declare in code.** `@solution("id")` on an interface and `@implementation("id", "name")` on each alternative (or
  `register(...)` for another package's class). Calling the interface runs the selected implementation; `using="name"` picks
  one for a call, `with override(...)` for a block, `ESOI_SELECT_<ID>` for a process, `[selection]` in `esoi.toml` for a
  deployment, and the solution's `selected` in the records is the project default. Unknown names fail with the choices and the
  layer that named them. The selection table and `Selector` remain the lower layer, and their names join the declared ones.
- **One copy of the default.** A table entry may omit `default`; the records' `selected` is used (`Selector.from_config`). Rule
  S23 compares only a table that still holds its own default. `esoi select --snapshot` writes the defaults for a package
  shipped without the records.
- **Records follow the code.** `esoi records sync` writes the solution and implementation rows the code declares and the records
  lack, never over text a person wrote; rule S30 reports the drift. `esoi new solution <id>` writes the records, a code skeleton
  with the decorators and an evaluation folder. The harness runs a declared implementation without an `impls/` wrapper.
- **Promote the winner.** `esoi select --promote` switches `selected`, the metric's command and the evidence in `selected_by`
  when a rival clearly wins on the solution's own metric and the solution's `promotion` cell is `automatic`, otherwise prints the
  exact proposal. It never acts on unverified, incomparable or stale rows.
- **Readable records.** `esoi check --write-docs` writes a `README.md` in each intent folder from its records; rule S8 keeps
  it current.
- **Simulated arms.** An arm that meters a deterministic stand-in for a model declares `SIMULATED = True`: its runs record
  model `simulated` and cost 0.0, `esoi run --stale` does not treat it as paid, and the leaderboard compares it on model calls
  instead of calling a known $0 baseline cheaper than an unknown cost (the false LOSS).
- `esoi init` writes the example declared in code.

Intents are the containers and the unit of hierarchy (from the author's updated SKILL.md):

- **Default folder `esoi/`.** A new project's specifications live in `esoi/` (the one constant `DEFAULT_STRUCTURE_DIR`); the name
  matches `esoi.toml`, `~/.esoi` and the skill. `structure/` and `docs/structure/` keep working when `structure_dir` names them.
  This repository's own `structure/` is now `esoi/`.

- The intent template now has the **Intent** itself (name, vision statement) as its own item, parsed beside the five
  specification templates; `esoi template sync` writes `docs/templates/intent.md`, an `intent.csv` header and the new
  definitions and principle bullets verbatim.
- **Layout.** An intent is a folder with an `intent.csv` and the five record files. The configured folder holds a project's
  **top intent**, which is why that project exists, in its own words (a product's is about the product, not ESOI; in this repository it is
  ESOI because that is why it exists). The evolvable structure a project applies is a **solution inside** its top intent, whose
  implementation may use esoi's solutions. A **sub-intent** is a subfolder with its own `intent.csv`; it arises as an
  implementation of a solution in its parent (`implements`, and `sub_intent` on that implementation) and states the
  `opportunity` that justifies it. `implementations.csv` gains `sub_intent` and `uses_solution_ids` (`@project_id/solution_id`
  for another project's solution). Ids are unique across the tree and links resolve anywhere in it. The folder default is one
  constant (`DEFAULT_STRUCTURE_DIR`).
- **Rules** S28 (intent folders and the sub-intent link) and S29 (ids across the tree, `uses_solution_ids`); S26 checks the
  records of every intent as one set, reports the retired `overall_solution_ids`, and a solution with
  `metric_kind` `specification` (defined, with alternatives, not yet measured by a run) needs no interface fields or metric command.
- **Legacy.** The two-level `overall` layout loads and passes as before, with one note pointing at
  `docs/guides/migrate-to-intents.md`. `esoi intent migrate [--apply]` moves the overall records into the top intent and
  turns `overall_solution_ids` into `uses_solution_ids`; it leaves the top intent's name and vision for the project to
  write and never invents a sub-intent.
- `esoi init` writes the intent layout: a top intent with its name and vision left empty (the check reports them until the
  project fills them), a starter `project-structure` solution that uses esoi, and no sub-intent.
- **Local ESOI index.** `esoi projects init|add|list|check|index|where` keeps `projects.csv` and a generated `INDEX.md` in
  `$ESOI_HOME` (else `~/.esoi`): which projects ESOI is applied to, how they relate and where to look first. No network calls.
  This repository records it as the `local-application-index` solution with a measured live implementation, the retired
  baseline of routing rows in a skill index, and the floor of each project's own records.
- This repository's own `structure/` is converted: top intent `esoi` with one sub-intent, `esoi-runtime` (the package as a
  runtime dependency of other people's code; its opportunity is marked unconfirmed). The earlier `esoi-python` and
  `esoi-for-ai-behaviour` sub-intents are folded back: their opportunities were not opportunities (the first mirrored top
  solutions one to one, the second repeated the goals and metric of `esoi-for-ai`).
- **Corrections after review.** A sub-intent's folder must be named by its intent id (S28). `esoi init` also writes a
  `project-purpose` top solution, left empty for the project, whose implementation builds on the project's other solutions;
  the structure is a solution inside the top intent, not the top. `esoi projects` reads a project's name and vision statement
  from its top `intent.csv` (the index cells are overrides for a project without one), reports a row that disagrees, derives
  `used-by` from other rows' `uses`, resolves `add .`, no longer guesses a name from legacy records, and reads
  `[tool.esoi]` in `pyproject.toml`. `esoi intent migrate` reports an overall solution with no implementation instead of
  dropping the dependency. The tracker folder name is configurable (`tracker_folder`) and never read as an intent.

Fixes from an adopter report (a verdict that compared different samples):

- The leaderboard compares arms only on the same cases and sample: the same `cases_sha`, the same new `sample` column (blank for
  the full set, `sample:N`, `only:ids`) and the same case count, so a log without the column still tells a 40-case run from a
  1,137-case one. Each rival is compared with the selected arm on the newest run both have; a rival with none is not compared
  (UNMEASURED, with the mismatch named) and `--strict` fails on it (`esoi leaderboard`, rule S20). Before, a 10-point gap between
  a full run and a 40-case sample was called WIN.
- `esoi run --stale` re-runs an arm on the sample its latest row used, and a rival on the selected arm's sample; `--full` runs the
  whole set. A rival on another sample is "not comparable", not stale.
