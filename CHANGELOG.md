- **A cascade runs one criterion: advisory rules S41 to S44, a floor that promotion never selects, and the lesson written down.** Joshua, 2026-11-04: "that's not how cascade is used, that could cause huge problems, every stage metric must be a single number which represents what alternative is best across all factors". The skill copies are synced (principle 12 and step 13) and two pages say it: the explanation `a-cascade-runs-one-criterion` (the file finding, topic needs and real inputs mistake, the correct shape, a checklist) and the how-to `write-a-cascade-that-stays-one-number`; the metric run policy and `CLAUDE.md` carry a short section. Four advisory rules inform with the next action and never fail `esoi check` (new module `esoi.rules.one_criterion`): **S41** a metric whose cascade has two or more stages and whose command scores more than one component (the cascade decides on one component's rows, so the others are a second criterion beside it); **S42** a solution with two or more metrics, each with recorded results for the same arms, ranked in separate leaderboards (make one authoritative and the others case sources); **S43** a solution whose `selected` names an arm marked `BASELINE` or `FLOOR` (a problem only where `[rules.S43] problem = true`); **S44** a `[balance.<component>]` table that changed in a commit of `esoi.toml` dated after the first row scored with it. `esoi select --promote` now refuses to propose an arm marked `BASELINE` or `FLOOR` as a winner or a first choice (`promote.floor_only`, `leaderboard.FLOOR_KINDS`); the scaffold's rival arm is now marked `ALTERNATIVE`, since it is a rival that can win. Not added: a solution with several metrics and no `authoritative_metric_id` is already rule R6, and whether a metric is aimed at what the solution is for needs a person's reading. Tests in `test_one_criterion.py`. Additive apart from the promotion refusal, so the next release is a minor bump.

- **`esoi follow`: a child repository follows its parent's selections and checks them with its own metric.** `esoi follow [--parent PACKAGE_OR_PATH] [--solution ID] [--plan] [--run-free] [--lock FILE] [--json]` compares, for every solution the child inherits or overrides, the parent's current selected arm (the `[parent]` table, a records folder, an `esoi_selection.json`, or an importable package whose Assembler has a parent chain) with the arm in the child's lock or its own `selected`, and judges the parent's arm on the child's own recorded rows by the child's own selection rule (`leaderboard.decisions` with its `[switching]` policy): `ADOPT` (drop the override or `esoi lock --update`), `KEEP THE OVERRIDE` (with the numbers), `OVERRIDE CAN BE DROPPED` (the parent's arm now beats the child's) and `NOT MEASURED` (the exact `esoi run <component> --impl <arm> --record` on the child's sample and its cost class). A row whose measured code changed under the child's staleness rule is shown as stale with its re-record command. It is advice only (exit 0; 2 only for an unreadable parent), prints one line when nothing changed, lists a malformed `overrides.csv` row without failing, and runs nothing unless `--run-free` is given, and then only arms the harness declares offline; a paid arm is listed, never run. `--json` prints `esoi.follow/1`. New module `esoi.follow`; no new record field. Tests in `test_follow.py`; how-to `follow-a-parent-repositorys-selections`, explanation `follow-the-parent-check-with-your-own-metric`. Additive, so the next release is a minor bump.

- **A cassette records and replays model calls: `--cassette DIR`, `--cassette-only`, `[harness] cassette`, `esoi cassette stats`.** Iterating on an LLM arm no longer repeats every unchanged prompt. With a cassette on (off by default), each call the meter wraps is keyed by a sha256 of the model, method and the arguments that affect the output (`timeout`, `request_id`, `metadata` and `user` excluded) and stored as one JSON line (response and usage: tokens, dollars, seconds) in `calls.jsonl`; a later identical call returns the stored response, is counted as replayed (`CallMeter.calls_replayed`, `replayed_tokens_in`, `replayed_tokens_out`, `replayed_cost_usd`, `replayed_seconds`) and is not part of the row's `model_calls`, tokens or cost; the row's `details` report the replayed cost apart. A miss calls the provider and records; a provider error and a response with no JSON form are not recorded; the file holds no request text and no key. An offline run still refuses a miss (`OfflineViolation`, counted as attempted) and allows a hit; `--cassette-only` raises `CassetteMiss` on a miss, so a variant that should be free proves it. `esoi cassette stats [DIR]` lists entries, hits, misses, size and the original cost of the stored calls. New module `esoi.cassette`, new `Config.harness` table. No model call. Tests in `test_cassette.py`; how-to `iterate-on-an-llm-arm-without-repeating-model-calls`; this repository's metric run policy counts a cassette-only run as a free stage. Additive, so the next release is a minor bump.

S39 reports a per-intent `min_lift` that fell and a per-intent `max_fan_out` or `max_names_per_sentence` that rose as adverse trends. - **Admitting a technology that does not fit: `esoi admit`, a written procedure with three worked examples, and a leaderboard that lists what has no arm.** `esoi admit <solution> <name> --why TEXT [--uses SOLUTION]... [--filepath FILE]` registers a newly found technology as an implementation row with no arm yet (empty `filepath`, the reason as its description, listed in the solution's `implementations`); `esoi records sync` fills the filepath once the code declares it. `esoi admit <solution> --changed WHAT --why TEXT` records a justified change to the specification (an interface widened, a solution added, merged or split, the hierarchy reorganized) as a dated line in the solution's `knowledge`; an empty reason is refused, and an unknown solution stops with the next move named. `esoi leaderboard` ends with the candidates that have no arm and no result, as `NOT MEASURED`, so what was left out stays visible. A how-to (`admit-a-technology-that-does-not-fit`) gives the decision steps, what a specification change may touch and how it is recorded; an explanation page says why. `tests/test_admit.py` walks a local model server (an arm), a reranker (a new solution and a stage of a composite arm) and an end-to-end memory product (a solution one seat up) through `esoi admit`, `records sync`, `check`, `select`, `lock` and `leaderboard`.

- **A `network` requirement and the outcome `pending-network`.** An arm that reaches the network declares `REQUIRES = (network("openalex.org"),)` (`from esoi.requirements import network`; the host is for the reader and may be empty). It is met in an ordinary run and unmet while `ESOI_OFFLINE=1`, which `esoi.entry`'s offline check and the harness set, with the remedy "needs network access; not attempted offline". The entry check then reports the id as `pending-network` instead of a `live-attempt` (or an error value the arm swallowed), and `pending-network` answers like `pending-key` and `pending-install` do; a live attempt still does not. The README example check treats it as pending too. Docs: the requirements reference and the entry outcomes in `declare-a-solutions-interface`.

- **Coherence evidence E2 counts executable code only.** `esoi.coherence` matched the used solution's id or interface class anywhere in a module's text, so a docstring or comment sentence counted as strong evidence that the code uses it, and a precision score could be raised by writing prose. E2 now reads the syntax tree: identifiers, attributes, imported names, annotations, decorator and call arguments and string literals used as values count; module, class and function docstrings, comments and any bare string statement do not. A module that does not parse falls back to its text with comment lines removed; only Python modules are checked, as before. Per-intent precision can fall where evidence was prose-only; the floors are measurements and are re-measured, not edited by hand. Tests cover the docstring gaming case and each evidence type; docs: how-to `declare-a-solutions-interface` and explanation `why-prose-is-not-code-evidence`.

- **A changed case file no longer fails `esoi check`.** S20 now separates a malformed row (no `git_sha`, or an unreadable `circumstances.csv`: `harness.defect_reason`, still a problem) from a staleness fact (other cases, changed code, uncommitted code, circumstances changed since the slice rows were derived: advice with the reason and the next action, listed by `esoi check --findings` and `esoi run --stale --plan`, never a failing line), and S33 is a problem only when the rows on the current cases and every well-formed row agree that the cascade chooses another arm (a choice that differs only because some results were recorded on other cases or changed code is advice), so editing a case file that names a moved module cannot block the move. Docs updated (choose-when-a-result-is-stale, metric-run-policy template, rules.md, CLAUDE.md).

- **A result is stale when what it measures changed, and a changed file informs instead of ordering a re-run.** The staleness rule is now a solution measured like any other (`know-what-a-result-measures`, in `esoi.staleness`) with three arms scored by the model-free `staleness_precision` component over a fixture of commits to a small git repository: `repo_wide` (any measured file, the old behaviour), `component_paths` (the files the ownership map gives the arm's solution and implementation, its evaluation folder and the shared fixtures; an unowned file counts for every arm) and `import_closure` (the repository files the arm's module imports, found by a static scan; a non-Python arm, a computed import or a changed non-Python file falls back to `component_paths`, and a component with no ownership entry keeps `repo_wide`, so a result is never silently fresh). A false-fresh decision is a hard fail that records the run as disqualified; the selection rule chose `import_closure` and disqualified `component_paths` (an undeclared shared utility). Set `staleness_rule` in `esoi.toml`; the default is the arm the records select, else `import_closure`. The stale reason names the changed file and its owner; `esoi stale --explain COMPONENT` and `esoi stale --count` show it. `esoi run --stale` now reports a row whose measured code changed and re-runs only what is worth running (a selected arm never measured, a declared expiration that has passed, `--for-decision` for the selected arms a decision or release depends on, `--include` for arms a person names); rivals and rows nothing depends on are listed as not re-run, and `--all` is the old run-everything behaviour. S20 and S10 findings about changed code, a stale rival or a missing row are advice that never fails `esoi check` or blocks a commit, and S33 no longer treats a changed file as an expired result. A recorded sha is marked dirty only for uncommitted changes the arm measures. Expiration stays never unless a metric or the project declares one. Offline runs refuse to start a model command (`claude`, `codex`, `gemini`) unless the arm is declared live (`PAID = True`, `paid_arms` or `--max-calls`): the refused attempts are counted in the row's details beside the metered calls and `ESOI_OFFLINE=1` is set. The metric run policy template and the how-to and explanation pages say when a metric is worth running and that no commit hook or CI step should run one.

The library reads the structure folder and the listed folders as one tree (`intents.folders`, `read_rows`, `discover`), so the rules, cascade, selection, assembly and tracker see one registry, and nothing is gathered or copied. `esoi records place|gather [--apply]` (`esoi.besidecode`) moves records to or from those folders, never out of the intent that owns them; `esoi records sync` and `esoi select --promote` write to the folder that holds the row; `esoi readmes` writes a README in every solution folder (the solution, its entry call and selected implementation, implementations linked to their code, metrics, links up and down, the diagram when the folders below it hold solutions it builds on). New advisory rule S40 informs (never blocks) where an opted-in repository deviates: spec and code more than one link apart, a code folder with no README, a record kept twice, each with its next action. `intent-registry` now has two measured arms, `esoi_folder` (renamed from `csv-records-in-the-repository`) and `beside_code` (renamed from `records-beside-the-code`), scored by the model-free metric `metric-navigable-records` (component `navigable_records`, one case per solution). Standard: `docs/reference/records-beside-code.md`; how-to: `docs/how-to/keep-records-beside-the-code.md`; template: `docs/reference/templates/solution-folder.md`. Both layouts work for a repository in any language (records reach code only through `filepath`; a non-Python repository records its entry call in `usage_notes`), and an implementation may be code, a reference or registry file that lists the files, services or practices that implement the solution, or a real-world system recorded as a registry row; a solution folder's README lists "Implemented by" generated from the records, the declarations and the ownership map, and S40 informs of a listed path that does not resolve or code missing from its registry. Functions `esoi.lock.write`, `update`, `diff`, `status`. The packaged snapshot (`esoi select --snapshot`) now carries each solution's `evidence`. The `rank_implementations` and `promote_the_winner` cases were updated with a note each and strict-policy cases added. No model call. - **Switch on a significant gain on the metric: `esoi.stats`, the paired rule in `esoi.leaderboard`, `esoi evidence-table`.** `esoi.stats` (standard library only) has `wilson_interval` (95% default), `mcnemar_exact`, `sign_test_greater` (the exact one-sided test), `holm`, `paired_counts` and `describe`. The library's whole switch rule: a rival replaces the selected arm when it is significantly better on the solution's authoritative metric on shared cases, by a one-sided exact paired test (McNemar for pass or fail per case, an exact sign test on paired per-case balanced scores), Holm-adjusted across rivals, alpha 0.05 (`leaderboard.decisions`, `verdict`, `challengers`; `Policy`, `policy_for`). Otherwise the selected arm stays and the verdict says "not shown better (p=..., k of n cases disagree); more cases would settle it". Without per-case rows, aggregate pass counts on the same cases and sample get Fisher's exact one-sided test (`stats.fisher_exact_greater`, named in the verdict).
